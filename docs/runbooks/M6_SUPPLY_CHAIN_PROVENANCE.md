# M6 — Supply Chain Provenance & Attestation Runbook

Status: PLANNED — EXECUTION BLOCKED BY M5A
Date: 2026-08-12
Authority: ADR-0060, `docs/architecture/ai-agent/AI_AGENT_SUPPLY_CHAIN_MODEL.md`, DEVELOPMENT Chain Execution Policy

## Goal

Bind one exact CAPITAL-AI source state to its dependency graph, SBOM, build result, artifact digest, provenance/attestation, release/deployment evidence and rollback artifact.

Canonical chain:

```text
source SHA
→ committed lockfile
→ deterministic dependency install
→ SBOM
→ tests/build
→ artifact digest
→ provenance
→ attestation
→ deployment identity
→ runtime identity
```

No M6 implementation or CI/workflow mutation is authorized until M5A is `COMPLETE / VERIFIED PASS`.

## Standards Baseline

M6 should implement against the current approved SLSA specification at execution time and record the exact version in Evidence. Documentation preparation uses SLSA v1.2 as the current approved baseline.

NIST SSDF SP 800-218 v1.1 remains the stable final baseline; later revisions/drafts may be tracked, but draft requirements must not be presented as final normative controls until adopted by a separate review.

OpenSSF Scorecard is supplementary automated evidence. A Scorecard result is not a substitute for source/artifact provenance, Human review or CAPITAL-AI policy gates.

## Required Outputs

1. exact source SHA;
2. dependency lockfile digest;
3. generated machine-readable SBOM (`SPDX` or `CycloneDX`); 
4. build/test result bound to source SHA;
5. artifact/image digest;
6. provenance statement identifying builder/source/build inputs;
7. verifiable signature/attestation when supported by the selected trusted build path;
8. dependency/security findings and disposition;
9. immutable reference to the last-known-good artifact for rollback;
10. Evidence bundle under `docs/evidence/m6/`.

## Target Assurance

Minimum intended posture:

- provenance generated by a hosted/trusted build path rather than a developer laptop;
- source and artifact digests cryptographically bound;
- build identity distinguishable from agent/model identity;
- signing/attestation key material unavailable to untrusted PR code;
- pinned immutable GitHub Actions where possible;
- explicit least-privilege workflow permissions;
- deterministic `npm ci` from committed lockfile;
- production dependency audit retained;
- no rebuild of an old release from mutable inputs for rollback.

Where the environment supports stronger isolated/hardened build guarantees, M6 may target the corresponding higher SLSA Build assurance only after the required controls are proven rather than inferred.

## Phase 0 — Read-only Preflight

Before implementation:

1. confirm M5A `VERIFIED PASS`;
2. resolve current `main`;
3. inventory build, Docker, npm and release workflows;
4. identify all third-party Actions and verify immutable pinning status;
5. inspect current package lock integrity and Node runtime contract;
6. inventory current SBOM/provenance/attestation tooling, if any;
7. inspect Render artifact/deployment correlation available at baseline;
8. classify proposed changes as C/R and identify any M7 mutation dependency;
9. define evidence and rollback before workflow changes.

## Phase 1 — Repository Implementation

Use a fresh branch from current `main`.

Implement only repository-side supply-chain controls, such as:

- SBOM generation;
- artifact digest export;
- provenance/attestation generation;
- verification scripts;
- workflow permission/action pinning where needed;
- Evidence manifest tying outputs to `${GITHUB_SHA}`;
- checks proving source/lock/SBOM/artifact consistency.

Do not perform Render/Stripe/Supabase external mutation in M6 unless a separately approved roadmapped requirement proves it is necessary. Deployment identity changes belong to M7.

## Required Positive Tests

- SBOM generated for exact current source/lock state;
- SBOM includes the expected top-level application identity and dependency inventory;
- provenance subject digest equals built artifact digest;
- source reference equals exact commit SHA;
- attestation verifies with expected builder identity/trust path;
- artifact chosen for rollback is retrievable by immutable digest/reference;
- workflow-security checks pass.

## Required Negative Tests

- changed source with stale provenance → DENY;
- changed lockfile with stale SBOM/provenance → DENY;
- artifact digest mismatch → DENY;
- unsigned/untrusted attestation when signature is required → DENY;
- unexpected builder/workflow identity → DENY;
- mutable/unpinned critical Action introduced → DENY according to repository policy;
- provenance/SBOM unavailable → release/deploy gate must fail closed where M6 requires them;
- agent/provider name claiming trust elevation → ignored/DENY.

## Evidence Contract

Create phase evidence under `docs/evidence/m6/` using the generic DEVELOPMENT Chain Evidence Template.

Evidence must include:

- final PR/head/merge SHA;
- CI run(s);
- SBOM format/tool/version and digest;
- provenance format/version and subject digest;
- attestation verification result;
- builder/workflow identity;
- artifact digest;
- dependency audit result;
- negative-test results;
- last-known-good rollback reference;
- branch deletion state.

Do not commit generated secrets, signing private keys or sensitive runtime credentials.

## Mutation State

External platform mutation: `NOT REQUIRED` by default for M6.

If a repository implementation discovers an unavoidable external mutation, M6 stops and produces a dedicated Roadmap/ADR/Runbook update before any such mutation is attempted.

## Rollback

Repository changes: new revert branch from current `main` → Human-reviewed revert PR.

Release/runtime rollback: use the previously verified immutable artifact/digest; do not rebuild old source using newer/mutable dependencies or toolchains.

## Exit Gate

M6 is `COMPLETE / VERIFIED PASS` only when:

1. M5A prerequisite was verified;
2. required repository controls are Human-merged;
3. exact source → lockfile → SBOM → artifact → provenance/attestation chain verifies;
4. required negative tests pass;
5. rollback artifact/reference is proven;
6. evidence is complete;
7. branch is deleted;
8. Roadmap/Traceability are synchronized.

Only then may M7 begin.
