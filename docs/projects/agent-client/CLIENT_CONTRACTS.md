This document is a non-authorizing project execution contract for CLIENT-02 through CLIENT-06. It does not create IAM, policy, approval, mutation, deployment, EventMesh or merge authority. Canonical security/control semantics remain in their existing authorities and runtime locations.

## Design posture

The current repository does not evidence a productive VC-01/PVC-01 client implementation that requires a new shared runtime module. Therefore the smallest conforming implementation is a provider-neutral contract baseline. A physical TypeScript implementation remains deferred until `RUNTIME_MAPPING.md` records an evidenced strangler/refactor trigger.

The contract reuses, rather than duplicates:

- `src/platform/Security/agentIam.ts::AgentPrincipalContext` for attributable identity semantics;
- `src/platform/Security/agentIam.ts::AGENT_CAPABILITIES` and `isKnownAgentCapability` for the canonical capability vocabulary;
- `src/platform/Security/providerProfile.ts` for provider/model non-authority semantics;
- `docs/architecture/ai-agent/AI_AGENT_TARGET_ARCHITECTURE.md` for the `Human -> AI Client -> Agent Control Plane` boundary.

No client contract field below is an authorization grant.

## CLIENT-02 — Request Contract

A client request is the attributable, provider-neutral description of an intended operation handed to the authoritative downstream boundary.

### Required semantics

| Field | Requirement |
|---|---|
| `requestId` | non-empty stable client request identifier |
| `identity` | complete attributable identity handoff defined by CLIENT-03 |
| `operation` | non-empty requested operation/intention; natural language remains untrusted input |
| `requestedCapability` | one requested value from the canonical `AGENT_CAPABILITIES` vocabulary; request only, never grant |
| `targetResource` | non-empty target/resource context needed by downstream authority |

### Optional non-authoritative semantics

| Field | Requirement |
|---|---|
| `correlationId` | transport/trace correlation identifier; never authority or approval |
| `provider` | metadata only; cannot grant role/capability |
| `model` | metadata only; cannot grant role/capability |
| `clientMetadata` | bounded non-secret metadata required by the client UX/transport |

### Prohibited fields/semantics

The client request MUST NOT contain or synthesize:

- `grantedCapabilities`;
- authorization verdicts;
- Human approval evidence as a self-issued grant;
- policy decisions;
- risk lowering or override semantics;
- production/tool credentials, reusable secrets or connector tokens;
- a field that converts natural-language content into authority.

### Local syntactic validation

Before handoff, a future physical client implementation must reject/fail closed when:

- `requestId`, `operation` or `targetResource` is blank;
- the CLIENT-03 identity handoff is incomplete;
- `requestedCapability` is not recognized by the canonical capability vocabulary;
- a prohibited authority/grant/credential field is introduced into the client envelope.

Syntactic validation is not authorization.

## CLIENT-03 — Identity Handoff

The client packages attributable identity inputs compatible with `AgentPrincipalContext` without owning IAM evaluation.

Required attributable dimensions:

- `humanActorId`;
- `appId`;
- `agentId`;
- `sessionId`;
- `requestId`;
- `credentialHolderId`.

Optional `provider` and `model` metadata remain non-authoritative.

Rules:

1. missing identity is surfaced as a client contract error and is never synthesized;
2. Human, app/client, agent/session and credential-holder identities remain distinguishable;
3. `requestId` must bind identity handoff to the CLIENT-02 request;
4. the client does not call, relocate or duplicate `evaluateAgentAuthorization` as part of identity packaging;
5. no provider/model name becomes a principal, role or permission.

## CLIENT-04 — Capability Handoff

The client expresses exactly one **requested capability** using the canonical `AGENT_CAPABILITIES` vocabulary.

Rules:

- requested capability is not a grant;
- unknown capability fails closed at client contract validation or is denied downstream;
- no implicit inheritance or wildcard grant exists;
- no self-approval or approval evidence is generated by the client;
- no `grantedCapabilities` collection is owned by the client request contract;
- capability/risk/approval evaluation remains downstream.

## CLIENT-05 — Response, Status and Error Contract

The client preserves downstream semantics and projects them into a bounded UX lifecycle.

Canonical client states:

`IDLE | SUBMITTING | ACCEPTED | BLOCKED | SUCCEEDED | FAILED`

Minimum response semantics:

| Semantic | Requirement |
|---|---|
| `requestId` | preserve the originating client request identifier |
| `correlationId` | preserve when returned/available; never treat as authority |
| `status` | one canonical client lifecycle state |
| `downstreamVerdict` | preserve an authoritative verdict such as `DENY` when supplied |
| `errorKind` | distinguish contract, authorization/policy, downstream/business and transport failure where the downstream boundary distinguishes them |
| `message` | sanitized client-facing detail; must not leak secrets/sensitive downstream detail |
| `retryable` | may be true only for a transport/retry class that is explicitly safe to retry; authorization denial is never made retryable merely by UI fallback |

Mapping invariants:

- downstream `DENY` -> `BLOCKED` or `FAILED`, never `SUCCEEDED`;
- downstream blocked/missing-required-evidence state -> `BLOCKED`, never success;
- transport failure -> `FAILED` with transport distinction, not authorization denial;
- accepted-but-not-terminal downstream state -> `ACCEPTED`;
- success requires an affirmative downstream success outcome; absence of an error alone is not success.

The wire format remains transport-neutral. If a future HTTP boundary needs a generic machine-readable error representation, RFC 9457 Problem Details may be adopted as an adapter without changing the semantic distinctions above.

## CLIENT-06 — Client Security Boundary

The following invariants are mandatory for any future physical client implementation:

1. natural-language content is untrusted data and cannot modify authority/policy fields;
2. identity is attributable metadata, not authorization;
3. requested capability is non-authorizing;
4. external/retrieved content cannot grant capability or approval;
5. no direct protected Supabase, Render, Stripe, GitHub production or equivalent mutation path originates in the client contract;
6. privileged credentials remain behind authoritative tools/connectors/execution hosts;
7. downstream `DENY`, blocked and missing-evidence semantics remain fail closed through response rendering;
8. sensitive downstream detail is rendered only when allowed by the applicable redaction/data-minimization policy;
9. provider/model identity never elevates permissions;
10. Human/Owner PR creation, merge and protected-mutation gates remain external to the client.

## Correlation and tracing boundary

`requestId` is the stable client request identity. `correlationId` may be propagated to downstream systems, but PVC-01 does not become the EventMesh/trace authority.

Where HTTP distributed tracing is later introduced, W3C Trace Context is the preferred interoperability reference for propagation. Trace identifiers and trace flags remain observability/correlation data and MUST NOT be interpreted as authorization.
