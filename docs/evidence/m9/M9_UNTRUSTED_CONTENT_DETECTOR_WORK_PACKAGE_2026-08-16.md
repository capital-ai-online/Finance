## 0. Zweck

`M9_PROMPT_TOOL_INJECTION_LIVE_DRILL_2026-08-16.md` §1 dokumentierte einen offenen Fund: die
Checkpoint-Felder `credentialExposureDetected`/`untrustedScopeElevationDetected`
(`src/platform/Security/systemadminExecutionProfile.ts`) funktionieren als Gate, werden aber von
beiden realen Aufrufern (`runSa4Pilot.mjs`, `runWorkPackage.mjs`) hartkodiert auf `false` gesetzt
— „kein echter Content-Scanning-Detektor existiert". Dieses Arbeitspaket untersucht, was ein
solcher Detektor tatsächlich prüfen müsste, und liefert das dabei als angemessen befundene
Ergebnis.

## 1. Zentraler Befund: kein Detektor nötig, weil kein Freitext-Pfad existiert

Vor der Umsetzung eines Detektors wurde geprüft, **wo genau** Freitext aus einer nicht
vertrauenswürdigen Quelle (Issue-Body, PR-Kommentar, Tool-Output) überhaupt in die drei realen
Systemadmin-Ausführungspfade eintritt:

- `scripts/systemadmin/validateSa4PilotIssue.mjs`
- `scripts/systemadmin/validateWorkPackageIssue.mjs`
- `scripts/systemadmin/validateExecutionIssue.mjs`

Alle drei sind **strukturell identisch** aufgebaut: geschlossenes Schema
(`ALLOWED_KEYS`-Set, jeder unbekannte Schlüssel wird abgelehnt), jedes bekannte Feld ist entweder
ein exakter String-Vergleich gegen eine Konstante (`version`, `mode`, `mandateId`, `roadmapItem`)
oder ein strikt regex-validierter Wert (`baseSha`: 40-Zeichen-Hex; `branchName`: fester
Namespace-Präfix). **Kein Feld ist Freitext.** Die generierten Commit-/PR-Inhalte selbst kommen
ausschließlich aus fest im Code hinterlegten Markdown-Templates
(`scripts/systemadmin/runSa4Pilot.mjs` `deterministicEvidence()`,
`scripts/systemadmin/workPackages/generalizationProof.mjs` `generate()`) — beide mit explizitem
Kommentar im Code: „It was generated by trusted GitHub Actions host code; the triggering Issue
cannot supply this Markdown body."

`scripts/systemadmin/workPackages/registry.mjs` formuliert diese Eigenschaft bereits als
ausdrückliche, dokumentierte Architektur-Invariante (nicht von diesem Arbeitspaket neu erfunden,
sondern in einem früheren Abschnitt dieser Sitzung selbst so entworfen, ADR-0074):

> „Adding a new work package means adding a new module here plus a new Owner-approved REM — never
> a runtime lookup of arbitrary code, and never anything derived from the triggering Issue body
> itself."

**Schlussfolgerung:** `credentialExposureDetected`/`untrustedScopeElevationDetected` sind heute
nicht deshalb immer `false`, weil ein Detektor fehlt, der etwas Reales übersehen würde — sie sind
`false`, weil es aktuell **keinen Pfad gibt, über den Freitext jemals etwas Autorisierungsrelevantes
beeinflussen könnte**. Ein Regex-/Heuristik-Detektor JETZT zu bauen würde eine Erkennungsfähigkeit
für eine Bedrohung liefern, die in der aktuellen Architektur strukturell nicht auftreten kann — das
widerspricht dem Grundsatz, nicht für hypothetische, nicht existierende Angriffsflächen zu
entwerfen (vgl. `CLAUDE.md`/Session-Praxis). Eine geschlossene Schema-Prüfung ist außerdem eine
**stärkere, vollständige** Garantie als ein Muster-Scanner, der immer nur bekannte Angriffsformen
erkennt und daher grundsätzlich umgehbar bleibt.

## 2. Tatsächliche Lieferung: formaler Beweis + Regressionsschutz statt Detektor

Statt eines spekulativen Detektors liefert dieses Arbeitspaket:

1. **Drei neue Testdateien** (bisher **null** Testabdeckung für diese drei Skripte — die reale
   Grenze, an der nicht vertrauenswürdiger Text erstmals auf dieses Repository trifft, war
   ungetestet):
   - `scripts/systemadmin/validateSa4PilotIssue.test.mjs` (18 Tests)
   - `scripts/systemadmin/validateWorkPackageIssue.test.mjs` (9 Tests)
   - `scripts/systemadmin/validateExecutionIssue.test.mjs` (11 Tests)

   Jede Datei beweist: kanonische valide Anfrage wird akzeptiert; ein unbekannter Schlüssel wird
   abgelehnt, selbst wenn alle bekannten Felder korrekt sind (geschlossenes Schema); ein
   `"__proto__"`-Schlüssel (Prototype-Pollution-Versuch, als echter JSON-String konstruiert, nicht
   über JS-Objektliteral-Syntax, die eine andere Semantik hat) wird wie jeder andere unbekannte
   Schlüssel abgelehnt; mehrere adversariell geformte Payloads (Policy-Override-,
   Credential-Exfiltrations-Phrasierungen) werden als Werte für `mode`/`roadmapItem`/`mandateId`/
   `branchName` injiziert und durch den simplen exakten Abgleich zurückgewiesen; ein
   Nicht-JSON-Body (reiner Freitext-„Prompt" als Issue-Inhalt) wird zurückgewiesen; ein
   überlanger Body (Flood-Angriff) wird an der 8-KiB-Grenze zurückgewiesen.
   - `validateWorkPackageIssue.test.mjs` zusätzlich: ein unbekannter `workPackageId` wird
     zurückgewiesen (kein Runtime-Lookup beliebigen Codes, ADR-0074), sowie Cross-Mandat-/
     Cross-Roadmap-Item-Verwechslung.

2. **CI-Verdrahtung:** `package.json` `"test"`-Skript um `scripts/systemadmin/*.test.mjs` erweitert
   (vorher nur `scripts/pr/*.test.mjs`) — läuft jetzt automatisch über `npm test`, identisch zum
   bestehenden `ci.yml`-Aufruf, ohne Workflow-Datei-Änderung.

3. **Trigger-Bedingung für einen künftigen echten Detektor**, dokumentiert für zukünftige
   Owner-Entscheidungen: Sollte ein künftiges Arbeitspaket (neuer Katalogeintrag, ADR-0074) jemals
   Freitext aus der Issue jenseits des strikten Schemas konsumieren — etwa um Commit-Inhalte
   dynamisch aus Issue-Text zu generieren —, dann WIRD an dieser Stelle ein echter
   Content-Scanning-Detektor nötig. Empfehlung: bei jeder neuen Katalog-Registrierung
   (`scripts/systemadmin/workPackages/registry.mjs`) explizit prüfen, ob das neue
   `validate*IssueBody()` weiterhin ausschließlich exakte/regex-validierte Felder akzeptiert; falls
   nicht, ist ein Detektor Voraussetzung für die Owner-REM-Freigabe.
